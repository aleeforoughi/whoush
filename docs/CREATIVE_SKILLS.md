# Whoush Professional Creative Skills v1.2.0

**Status (P2):** all 22 skills (15 base in `lib/skills.ts` + 7 in `lib/advanced-skills.ts`) now drive a private, typed orchestration layer used by `/api/agent`: `lib/orchestrator.ts` (safety -> `preparePrivateCreativeRequest` -> planner -> invariants -> plan inspection -> proposal), `lib/creative-plan.ts` (zod contracts, public projection), `lib/private-audit.ts` (hash-only audit) and `lib/llm-anthropic.ts` (live adapter). Live planning is off by default and fail-closed (`llmPolicy` in `lib/llm.ts`: needs `LLM_PROVIDER_AUTHORIZED=true`, `ALLOW_LIVE_LLM=true`, a configured `claude-*` model id and key); otherwise a deterministic, no-network planner is used. Camera/shot fields are proposed creative direction, not EXIF or verified provider controls. The registry version is `SKILL_REGISTRY_VERSION` in `lib/skills.ts`.
Owner requirements: permanent knowledge modules for auto-routed *private* LLMs; all creative output belongs to Higgsfield media models, never to the reasoning LLM. Users do not choose or see reasoning model names.
Skills source of truth: `lib/skills.ts`. Safety: `lib/safety.ts`, `docs/MODERATION_POLICY.md`.
This is a reusable skill instruction library, not retrained model weights or a searchable retrieval database. The latter must be implemented separately for reference-heavy knowledge and trends.

## Mandatory foundation on every creative turn
- `prompt_engineer`: structure intent, preserve hard/soft constraints, optimize prompts for capabilities.
- `creative_director`: coherent art direction, creative consistency, audience fit.
- `persian_language`: accurate Persian reading/writing, dialect and register, RTL and bilingual text. Listening/speaking only when actual supported audio inputs and outputs exist.
- `qa`: pre-plan and post-generation checks; no claiming actual quality without inspecting rendered assets.

## Always-on photography rule
If user asks for a NEW still image, the internal planning prompt must provide a proposed:
- camera/look and lens focal length; camera distance and perspective;
- f-stop/aperture, shutter speed, ISO, white balance, focal plane, depth of field;
- framing, subject placement, aspect ratio and horizon;
- key, fill, back/rim and practical light directions, qualities, reflections/shadows;
- mood/color pipeline, subject realism and final output QA.
These are **creative directions**, not actual captured EXIF, and not guaranteed controllable knobs for Higgsfield. The agent maps controllable parameters only after checking the selected provider model's actual documented schema.

For INPUT image edit, preserving the source **overrides** invented photographic settings. Do not rewrite original lighting, camera geometry, face, hair, pose or motion without explicit consent.

## Always-on video rule
Any video task gets cinematography and videography. Establish shot scale, lens character, movement trajectory, motivated blocking, exposure, WB, target FPS/shutter, blur, duration, cuts, source references and color continuity. If editing video, use additional video-editor skill and protect source PTS/FPS, audio, camera, framing and foreground edges as requested.

## Source of truth / trend retrieval
Do not treat static training as live Instagram/TikTok/X trends. The social skill may request a licensed retrieval connector/search with timestamps; if none available, present evergreen platform conventions without saying they are current. Validate geography, idioms, translations, poem sources and celebrity/nonpolitical identity references. Respect artist rights and consent.

## Quality gates
- Before LLM: safety decision, account/media eligibility, model budget, reference ownership. Reject blocked and hold for review on ambiguous.
- Before generation: typed action and explicit supported media model, exact input IDs, source locks, whole-Neuron SKU, user quote approval.
- After generation: objective metadata checks, relevant visual QA, text verification, user acceptance.
- Retain skill registry version and selected IDs **privately** per job for QA and reproducibility. Do not expose LLM vendor/provider or internal token pricing.

## Efficient LLM use
Haiku-tier private reasoning for brief triage / simple tool classification, Sonnet-tier for everyday creative planning, Opus-tier for complex identity/temporal plans and multi-shot creative direction, with private configurable routing based on budget and capability. These are suggestions for *reasoning tier* not hard-coded public provider product names. Do not use expensive multi-agent debate per prompt. Escalate only based on uncertainty or validation failure; deterministic systems own payment, moderation hard rules and authorization.

## Attachments
Users can attach files to a chat message (`lib/attachments.ts`, `lib/attachment-files.ts`, `components/attachment-tray.tsx`). Limits: 10 files and 200 MB per message; image 20 MB (JPEG, PNG, WebP), video 100 MB (MP4, MOV, WebM), audio 25 MB (MP3, WAV, M4A, OGG, WebM), PDF 20 MB, JSON 1 MB, Markdown 1 MB.

**Verification.** The browser decides what a file is from its leading bytes (magic numbers), never from its name or declared type. A declared type or extension that disagrees with the bytes, SVG, HTML, executables and empty files are rejected with a Persian reason. JSON and Markdown must be valid UTF-8, and JSON must parse. The server re-validates the metadata with a strict schema (`AttachmentSchema` in `lib/creative-plan.ts`), but it never sees the bytes, so the byte check is a user-experience and consistency gate, not a security boundary.

**Tags and mentions.** Every attachment gets a stable tag for the conversation. Internally (wire, schema, audit, the live planner's `<attachment tag="image1" …>` blocks) it stays English: `image1…` (images), `video1…`, `audio1…`, `file1…` (PDF, JSON, Markdown); the wire pattern is `/^(image|video|audio|file)[1-9]\d?$/` (1 to 99 per prefix). Users always see and type the Persian form with a `#` prefix, an ASCII hyphen and Persian digits (`displayTag`):

| Kind | Internal tag | Shown and inserted |
|---|---|---|
| image | `image1` | `#تصویر-۱` |
| video | `video1` | `#ویدیو-۱` |
| audio | `audio1` | `#صدا-۱` |
| pdf, json, md | `file1` | `#فایل-۱` |

Numbers only count up (`allocateTag`), are never reused after a removal, and "new chat" starts again. The schema requires the prefix to match the kind and the tags of a request to be unique.

Parsing (`parseMentions`, `splitMentions`, `rewriteMentions`) is case and script tolerant: the prefix is `#` or `@`; the word is تصویر, ویدیو (or ویدئو), صدا, فایل or the legacy English `image|video|audio|file`; an optional hyphen (also U+2010, U+2011, U+2013, U+2212, or a ZWNJ or nothing at all) follows the word; the number is 1 to 99 in Persian, Arabic-Indic or ASCII digits, so `#صدا-۱`, `#صدا۱`, `#صدا1`, `@image1` and `@image-1` are the same mention. Arabic ي/ى and ك are read as ی and ک, and ZWNJ or tatweel inside the token is ignored. A mention must start the text or follow whitespace or punctuation, and must not be followed by a letter or digit, so `#تصویر-۱،`, `#صدا1` and `@image1` match, while `#نوروز`, `email@image1.com`, `#تصویر-۱۲۳` and `#تصویر-۰` do not. Every accepted spelling names the same internal tag.

In the composer, chips show the tag as `#تصویر-۱` (click it to insert it at the caret). Typing `#` (or `@`) at the start of the text or after whitespace opens a combobox of every attachment still in the conversation (this message's tray plus earlier sent ones); it filters by the Persian or English word with either digit set (`#تص`, `#صدا`, `#صدا-`, `#im`), and choosing an option writes the canonical `#تصویر-۱ `. An ordinary hashtag such as `#نوروز` is not the start of any tag word, so the list closes (`mentionTrigger`). In a sent message each mention is a Badge showing the Persian tag, and a tag that names an attachment opens its preview (image, video) or details. Per-chip errors, aria-labels, the plan «مراجع» list (formatted on the client from the public `references[].tag`) and the missing-mention question all use the Persian form. The request carries this message's new attachments plus any earlier sent attachment mentioned in the text in any accepted spelling (the same wire metadata and excerpt as when it was first sent, never bytes), within the 10 file and 200 MB limits. A mentioned tag with no attachment never blocks: the plan gets a Persian `clarifyingQuestionFa` such as «پیوست #تصویر-۳ در این گفت‌وگو پیدا نشد؛ …». In the English `mediaPrompt` each mention, however it was typed, becomes a description such as `[reference image 1 · character]` or `[motion reference video 1]`; the public Persian text keeps what the user typed, and the role lines in the plan name the attachment as `#تصویر-۱`.

**Roles are optional.** Choosing a role (نقش) for an image, video or audio is never required, and neither is using a `#` mention. Each chip's role Select starts at «انتخاب اتوماتیک هووش» (Whoush picks automatically) and the user can switch back to it after choosing one. Nothing blocks sending: there is no role or consent check in the UI. Files have no role. The wire uses the English id (the schema makes `role` optional for media and rejects `general`); the UI uses the Persian label. A role the user chooses is recorded with `roleSource: "user"`.

**The + menu.** Inside the prompt field, at the inline-start edge (right in RTL), a `+` button («افزودن پیوست یا مرجع») opens a Notion-style insert menu: a Feather `Popover` anchored to the button, opening upwards, with a **search field on top** («جستجو…») that filters as you type and the entries below, scrolling within about 55dvh (`components/insert-menu.tsx`). It is an ARIA combobox: focus starts in the search field and stays there, ArrowUp/ArrowDown move the active option (announced through `aria-activedescendant`), Enter picks it, a click picks it, Escape closes and returns focus to `+`. The filter (`filterInsertMenu` in `lib/insert-menu.ts`) keeps an entry when every word of the query appears in its title, hint or group label (so «ویدیو» lists every video entry), folding Arabic ي/ك, ئ/ؤ/أ/آ, ZWNJ, tatweel, diacritics and Persian digits; with nothing left it shows «گزینه‌ای پیدا نشد». **«پرکاربردترین» is hidden for now** (`SHOW_POPULAR = false`, owner 2026-11-05); while it is hidden, «رفرنس اتوماتیک» sits alone at the top, since it is the only menu entry that uploads without a role. The inline-end edge has the icon-only send button; Ctrl/Cmd+Enter also sends (not while the `#` mention list is open). Above the field sits the chip tray; the selected-character chip (with an edit link and a clear button) is in the panel header; under the field sit two outline pills, the build mode and «سبک». The menu is the pure data in `lib/insert-menu.ts` (`INSERT_MENU`), built from the role table below, so every UI role appears exactly once in its kind group (plus the «پرکاربردترین» shortcuts), in this order:

- **پرکاربردترین** (hidden for now, `SHOW_POPULAR = false`): رفرنس اتوماتیک (any file; no role is sent and inference applies)، عکس رفرنس، شخص، فریم، پوشاک، الگوی گفتار. These shortcuts repeat entries of the groups below with the same action (`POPULAR_IDS` in `lib/insert-menu.ts`);
- **تصویر** (owner list, 2026-11-05; renamed 2026-11-06): عکس رفرنس، شخص (the character role)، کاراکتر (opens a dialog of the saved characters with the same usability rules, disabled reasons and an empty state linking to `/characters`; choosing sets `characterRef`, the chip, `?character=` and `sessionStorage` `whoush-character`), پیرایش، پوشاک، محیط، اشیا، گرافیک، فریم;
- **ویدیو**: فیلم رفرنس، الگوی حرکت;
- **صدا**: الگوی گفتار، موزیک;
- **فایل**: فایل (PDF, JSON or Markdown, as context).

**Upload cards.** Picking any upload entry (everything except «کاراکتر», the saved characters) does not open the file picker directly: it adds an empty upload card **inside the prompt field**, above the text, and moves keyboard focus to its upload button (`lib/upload-slots.ts`, `components/upload-slot.tsx`). The card is an empty state: transparent with a faint dashed border. Its upload button holds the upload icon with the category name under it (تصویر، ویدیو، صدا، فایل، or «هر نوع فایل» for the automatic card) and a small **category** icon in its top start corner, top right in RTL (a paperclip for the automatic card; a کاراکتر card shows the image icon there). The role's own icon and name are in the role row at the bottom. Each card also shows the tag its file will get (`#تصویر-۱`): the tag is reserved when the card is made and used by the file that fills it. **Tag numbers are the lowest free ones** (`lowestFreeTag`): removing a card or a file frees its number, so with `#تصویر-۱` and `#تصویر-۲` in the composer, removing `#تصویر-۲` and adding a photo gives `#تصویر-۲` again. Numbers used in sent messages stay taken, so a mention in the history never points at a different file. The automatic card has no tag until its file arrives, since its kind is not known yet. Its one strong element is that upload button, filling the 16:9 media area where the thumbnail will appear (neutral secondary fill with a solid 3:1 border; never the blue primary, which belongs to send; accessible name «آپلود کاراکتر») that opens the picker for that kind, single file. «یا فایل رو اینجا رها کن» is the button's description for screen readers; a file dropped anywhere on the card fills it. An accepted file **fills the card in place**: it stays inside the prompt field and becomes a file card (`components/attachment-card.tsx`) with the thumbnail on top (a button that opens the full-screen viewer; audio and documents show a large kind icon and the name), the tag (a button that inserts it into the prompt) with the duration for audio and video, the role row and, for a lip-sync audio, language and accent. **A role the user chose is fixed:** the card shows it as text, with no menu; to change it, remove the card and add another. A file with no role (the automatic card, or a file dropped or pasted) keeps an optional role menu, and once a role is picked there it is fixed too. **Empty and filled cards are the same size** (`CARD_*` in `components/attachment-card.tsx`): 12rem wide, a 16:9 media area on top (when empty, the upload button with the upload icon and the category name inside it; when filled, the thumbnail), a tag row, and a 44px role row with no frame: the role's icon at the start (right in RTL), the role name, and a small delete × at the end (left in RTL; 28px to the eye, a 44px touch target). Every card in the row stretches to the tallest one, so a lip-sync card with its extra menus still lines up. Files added any other way (dropped on the composer, pasted) appear as file cards too, after the «+» cards, so every file of the next message is a card inside the field; the tray above it only shows problems, the count and the privacy note. Removing a file card removes the file; a file of the wrong kind is rejected with «این گزینه فقط تصویر می‌پذیرد» and the card stays for another try. The small × in the role row («حذف کارت لباس و کفش» on an empty card, «حذف <file name>» on a filled one) removes the card; on an empty card focus returns to the prompt. Cards plus attached files never exceed 10 per message; empty cards hold no file and are dropped on send, new chat and project switch. Cards use the 8px control radius (they sit inside the 8px field). Measured: upload button content 12.9:1 light and 15.7:1 dark, button border 3.2:1 and 3.3:1, role text at least 5.97:1; the dashed card border is deliberately faint (decorative, 1.2-1.6:1), since the button carries the affordance.

**Style (`style`).** Under the field, beside the build mode, an outline pill «سبک» shows only the current style («سبک: اتوماتیک» by default) and opens a radio menu: اتوماتیک («هووش سبک را از متن تشخیص می‌دهد»)، واقع‌گرایانه («مثل عکس واقعی، بافت و نور طبیعی»)، سه‌بعدی («رندر سه‌بعدی تمیز»)، کارتونی («کارتونی و رنگی») (`lib/style-setting.ts`, `components/style-control.tsx`). It is a setting, remembered in `localStorage` key `whoush-style`; اتوماتیک sends no `style`. `CreativeTurnInputSchema` accepts `style?: "realistic"|"three_d"|"cartoon"`. It wins over `visualStyle` and over style words in the text (with neither set, the text detection of «انیمه», «کارتونی»… is unchanged): `realistic` is `photoreal` (`hyper_realism` on) with the soft preference «سبک واقع‌گرایانه: بافت، نور و رنگ طبیعی»; `three_d` and `cartoon` are `stylized` (`hyper_realism` off) with the directives «رندر سه‌بعدی تمیز با متریال فیزیکی، نور نرم و سایهٔ طبیعی؛ بدون بافت پوست عکاسی یا نویز» and «سبک کارتونی: خطوط تمیز، فرم‌های ساده و پالت رنگی هماهنگ» (English in the provider prompt: `3D render style: physically based materials, soft global illumination, clean shading`, `cartoon style: clean outlines, simplified shapes, harmonious vivid palette`). With a character reference (Character Studio or a `character` image) and `three_d` or `cartoon`, the constraint «هویت کاراکتر در سبک انتخاب‌شده قابل تشخیص می‌ماند» is added. A planner that drops these lines gets them back (audit correction `style_directives`). The public plan carries `style` and plan details show «سبک انتخاب‌شده»; the audit records it.

**Build mode.** Under the field, an outline pill «حالت ساخت» shows only the selected mode and opens a radio menu (اقتصادی · سریع · با کیفیت). Each mode is outlined in its own color, text, icon and border alike (اقتصادی green/success with coins, سریع orange/warning with a bolt, با کیفیت blue/info with a gauge), never filled, so the send button stays the only filled control. The light brand tokens darken success (#1E7D46) and warning (#C2410C) and info (#2A6CB8) so all three pass AA as text on the background and the card surface. It sends `preference` `cost`, `speed` or `quality` (default) with every `/api/agent` request (`lib/mode.ts`, `components/mode-control.tsx`). It is remembered in `localStorage` key `whoush-mode` (read with `useSyncExternalStore`, errors ignored). Changing it while a proposal is on screen does not change that proposal; a hint says the new mode applies from the next message.

Each role entry opens one hidden multi-file input restricted to that kind's accept list (`acceptFor`); every file picked that way gets the entry's role with `roleSource: "user"`, and a file whose real type (magic bytes) is another kind is rejected with a Persian reason. The count, size, sniffing and error rules are unchanged. The chip's role Select (including «انتخاب اتوماتیک هووش») remains the only place to change a role afterwards; drag-and-drop onto the panel and paste add files with an automatic role. Voice cloning is not offered anywhere in the UI; the server still refuses it (below).

**Inference (`inferAttachmentRoles`).** Without a chosen role the orchestrator guesses one from the words of the brief, before skills resolve, and records `roleSource: "inferred"`. It uses words only: no image, video or audio is analyzed, and none can be until the media-inspection step exists. The context is the clause around the attachment's mention in any accepted spelling (clauses end at `. ، , ؛ ; ? !` and newlines; when two mentions share a clause, the words between them are split between the two, the earlier mention keeping the first half), or the whole text when the attachment is not mentioned. The text is normalized with `normalizePersian`; Persian and English keywords match as whole words (a Persian keyword may take a plural or possessive suffix such as ـی, ـها, ـام). The first matching group wins, in this order:

| Kind | Order (first match wins) | Persian keywords (English keywords alongside) |
|---|---|---|
| image | `edit_reference` | ویرایش، ادیت، حذف کن، پاک کن، جایگزین، عوض کن، تغییر بده، رتوش |
| | `end_frame` | فریم آخر، آخر ویدیو، تهش، پایان ویدیو، ختم بشه به، برسه، برسد، تمام بشه (end frame, last frame, ending) |
| | `start_frame` | شروع کن، شروع از، شروع بشه، متحرکش کن، زنده‌اش کن، جون بده، انیمیت، متحرک کن، تبدیل به ویدیو (animate, bring to life, make it move, start from) |
| | `outfit` | لباس، مانتو، کت، شلوار، پیراهن، دامن، کفش، پوشش، ست لباس، استایل لباس (outfit, dress, clothes, wardrobe) |
| | `hairstyle` | مدل مو، مو، رنگ مو، کوتاهی مو، ریش، سبیل، فرم ریش، پیرایش، اصلاح (hairstyle, haircut, hair, beard, moustache, grooming) |
| | `makeup` | آرایش، میکاپ، رژ، رژ لب، سایه چشم، خط چشم، ریمل، ابرو (makeup, lipstick, eyebrow) |
| | `character` | کاراکتر، شخصیت، چهره، صورت، پرتره، این آدم، این فرد، خودم |
| | `graphic` | لوگو، پوستر، گرافیک، تایپوگرافی، فونت، متن روی، بنر |
| | `object` | محصول، شیء، اشیا، کالا، کیف، بطری |
| | `environment` | محیط، فضا، مکان، لوکیشن، پس‌زمینه، اتاق، خیابان، منظره |
| | else `general` | |
| video | `edit_reference`, then `continue` (امتداد، ادامه بده، ادامهٔ ویدیو، طولانی‌ترش کن، ادامه‌اش; extend, continue), then `motion_reference` (حرکت، رقص، الگوی حرکت، کپی حرکت، مثل این حرکت), else `general` | edit words as for images |
| audio | `lip_sync` (لب، لیپ سینک، لیپ‌سینک، دیالوگ، گفتار، صحبت، حرف بزند), then `music` (موسیقی، موزیک، آهنگ، ریتم، بیت، ملودی), else `general` | |

A phrase such as «آرایش این عکس روی چهره‌ام» resolves to `makeup`, not `character`, because the beauty roles are checked first; with two mentions in one clause (`از #تصویر-۱ شروع کن و به #تصویر-۲ برسه`) the words between them are split, giving `start_frame` and `end_frame`. Cosmetic colors such as «آرایش نود» are allowed by the safety preflight.

`voice_clone` is never inferred and is not offered in the UI. `general` is an internal role only: it is not in the UI Select and the wire schema rejects it. For an inferred `lip_sync`, the speech language and accent default to `unknown` and `unspecified`, so the Tehrani skill never activates from inference alone. Inferred roles drive exactly the same skills, constraints, kind override and requirements as chosen ones. The public plan marks them: `references[].roleSource` is `user` or `inferred`, and «مراجع» shows inferred ones with a suffix, e.g. `#تصویر-۱ · کاراکتر (انتخاب هووش)`.

**Category roles resolved from the brief** (owner decision, 2026-11-05). Two menu roles are categories, not instructions; `inferAttachmentRoles` narrows them before planning (`roleSource` stays `user`), so the planner, skills and constraints only ever see the concrete roles in the table below:
- `reference` (image «عکس رفرنس» · «ظاهر، سبک یا محتوا؛ هووش از متنت می‌فهمه»; video «فیلم رفرنس» · «ادیت، امتداد یا حال‌وهوای همین ویدیو؛ از متنت مشخص می‌شه»): `edit_reference` when the words around its mention ask to change it (the edit keywords below); a video becomes `continue` when they ask to extend it; otherwise `general` (a loose look, style or composition reference).
- `frame` (image «فریم» · «فریم اول یا آخر ویدیو؛ از متنت مشخص می‌شه»): `end_frame` when the words around its mention say so (فریم آخر، ختم بشه، برسه…), `start_frame` when they say so (شروع کن از، متحرکش کن…); frames with no hint fill the free slots in order, so two unhinted frames are first and last. A single frame that is not mentioned reads the whole brief; with no hint it is the start frame.

Roles that left the menu (`start_frame`, `end_frame`, `makeup`, image and video `edit_reference`, `continue`) stay valid: Whoush still infers them, the wire still accepts them, and sent messages and older projects keep their labels. «لباس و کفش» is now «پوشاک» and «لوگو و گرافیک» is «گرافیک»; their ids are unchanged.

If the text sounds like an image request but there is a video attachment, or an audio with `lip_sync`, the media kind is video (a comment in `orchestrateCreativeTurn` says why). Role constraints are enforced by the plan invariants: a planner that drops one gets it added back (audit correction `role_directives`). The public plan has `references: [{tag, kind, role, roleSource, labelFa}]` (never ids, hashes or names), shown in plan details under «مراجع».

**What is sent** with the request: per file an id, tag, kind, mime, size, sha256, optional pixel size or duration, the role (media only, optional), `consent: true` for `voice_clone` (API clients only; the UI never sends it), the speech details (language, accent) for `lip_sync` only and, for Markdown and JSON only, a text excerpt of up to 8000 characters. **What is not sent:** file bytes and file names (the schema rejects a `name`). Files stay in browser memory for the session; nothing is stored or uploaded.

**How the server uses them.** Excerpts are run through the safety preflight like the prompt (a blocked excerpt restricts the turn before any planner runs). They reach the private planner only inside `<attachment>` blocks within `<user_brief>`, with forged tags stripped: media and PDFs as `<attachment tag="image1" kind="image" role="character"/>` (no content), Markdown and JSON with their excerpt. The blocks carry `role` and `role_source` (`user` or `inferred`). The skill instructions mark all of it as untrusted data, say that tags name the user's files and that roles are hard constraints, and that an inferred role is a best guess the planner may refine only in hard constraints and never escalate to `voice_clone`. The private audit keeps only `{tag, role, roleSource, kind, bytes, sha256}`.

**Order of outcomes.** (1) Safety on the text and excerpts. (2) Plan and plan inspection. (3) Any `voice_clone` attachment returns status `unsupported` with «کلون صدا در هووش پشتیبانی نمی‌شود؛ هووش فقط تصویر و ویدیو می‌سازد و تولید یا شبیه‌سازی صدا ممکن نیست.» (HTTP 422), audit reason `voice_clone_unsupported`, no price. (4) Else any image, video or audio attachment fails closed: the plan is returned with `no_compatible_model` (HTTP 422), no proposal and no price, audit reason `media_review_unavailable`, because no image, video or audio inspector exists yet (`docs/MODERATION_POLICY.md` steps 4 and 6). (5) Else the proposal; files-only turns stay `planned` with a price.

**Model suggestions (P5).** On outcome (4) and on `no_compatible_model`, `mediaRequirements` also names a specialised `operation` from the roles (a `lip_sync` audio is `lip_sync`; an `edit_reference` video with a `character` or `object` image is `replace`; a `motion_reference` video with an image that is not a `graphic` is `motion_transfer`). When the catalogue has a model for it, the result carries `suggestedModel: {name, active:false, blockersFa}` (raw name only: Intone or Genjutsu) and the Persian message ends with «مدل مناسب این کار: <name>؛ پس از تأیید فعال می‌شود.». It is never a proposal: no price and nothing to approve, and the UI shows it with a «به‌زودی» badge. Voice cloning, `start_frame`, `end_frame`, `continue`, `outfit`, `hairstyle` and `makeup` get none.

**Capability flags (unverified).** `motionReference`, `videoReference`, `startImage`, `endImage` and `videoContinuation` are model capabilities and requirements (`lib/catalog.ts`, `lib/router.ts`). No model has evidence for them (the agent-catalogue entries for Intone and Genjutsu do not claim them either), so every model records `false` and can never satisfy them; they are for when the media-review stop is lifted. Reference-image requirements already count every attached image.

**PDF.** PDFs are accepted and counted, but their text is not extracted (no parser dependency yet); the plan states that the PDF has no effect.

## Chat messages
- **User messages** sit on the right (the start in RTL) in a filled grey bubble with no border (`bg-secondary`: dark grey in dark mode, light grey in light mode). Their files appear above the bubble as the same cards the user built in the chat input (`SentAttachmentCard`: same size, thumbnail, tag and role row with its icon), read-only: the thumbnail opens the viewer, the tag inserts itself into the prompt.
- **Agent messages** are full-width plain text with no bubble. Only cards that carry an action (the live proposal, past proposals, no compatible model) have a container; a restricted request is plain text with an info icon.
- **Action bar** under every message (user and agent): copy, «اجرای دوباره» and the time («۶ دقیقه پیش»; the full Jalali date and time in the tooltip). Icon-only, with each name in a tooltip and as the accessible name. It keeps its space but stays invisible until the pointer is over the message or focus is inside it; on touch screens (no hover) it is always shown.
- **«اجرای دوباره»** sends the user message again as a new turn (for an agent message, the user message it answered), with its files and the current mode, style and character. The draft and the cards in the chat input are left alone.

## Generations
- **Tags.** Every generation plan (proposal) in a chat gets a tag, `generation1` on the wire and «#تولید-۱» in the UI, numbered per chat. Proposals saved before tags existed get the next free tags in order when the project opens. A generation can be referenced only from its own chat.
- **Card.** The generation card is short and actionable: kind, tag, model (recommendation first, alternates marked «جایگزین», each with fixed Neurons), then [بساز · N نورون] and [اصلاح] (text only). A past card (expired quote) keeps only «اصلاح». The no-compatible-model card shows only the model that fits but is not active yet.
- **«اصلاح».** Puts only the generation's tag («#تولید-۱») into the prompt as a dismissable badge, where the user writes the changes; the mention is what refers to it (up to 3 generations per message). The request carries `generations: [{tag, mediaKind, summaryFa}]`; `summaryFa` is built in the browser from the stored public plan (kind, model, intent, style, camera or shot, key constraints and preferences; never the private media prompt), is safety-checked like an excerpt, and reaches the planner only as a `<generation>` data block. The planner revises it: only the asked changes, the same media kind unless the brief asks for the other one. An unknown generation tag becomes a clarifying question.
- **Plan in the conversation.** The plan is no longer inside the card: it is part of the agent's message, with icons. It covers the clarifying question, intent, references, the staging diagrams, the camera or shot settings as icon chips and lines, and the hard constraints; preferences, identity lock, continuity, speech and QA fold under «جزئیات بیشتر».
- **Staging diagrams.** Plans carry an optional structured `staging` block (camera angle, shot size, 1 to 4 lights with direction as seen from the camera, height, soft or hard, source, kelvin and an optional gel colour). The browser draws it locally as SVG: a side view of the camera angle, the frame cut at the shot size and aspect ratio, and a top view of the lights in their colours. LLM planners are asked to fill it; a missing block is filled from the deterministic plan without counting as a correction, and an invalid one is dropped, never fatal. Diagrams illustrate Whoush's proposal, not provider settings.

## Prompt input
- The prompt is a plain-text editable field in which every `#` mention of a file or generation of the chat is an inline badge with a small × (Backspace or Delete also remove it as one unit). A typed tag becomes a badge once the caret moves past it (a space, or picking it from the `#` list), so `#تولید-۱۲` can still be typed; an unknown tag or an ordinary hashtag stays text. The value stays plain text: a badge counts as its canonical tag (`#تصویر-۱`). The model lives in `lib/mention-editor.ts`.

## Questions
- Whoush asks only when a critical requirement is missing and no reasonable default exists (no subject at all, two fundamentally different outputs equally likely, or a mentioned file or generation that is not in the chat). Everything else, including style, composition, camera, lighting, colours, aspect ratio, duration and missing character angles, is decided by Whoush and stated in the plan; it never asks about micro decisions and asks at most one question.
- A question stops the turn (`needs_input`, HTTP 422 `{error:"needs_input",question}`): no plan card and no price. The question is the last item of Whoush's message and, while unanswered, carries a flashing «نیاز به پاسخ تو» badge (static under reduced motion).
- The answer is sent with the original request (`answerBrief`) and `answersQuestion: true`; such a turn is never asked about again. Whoush decides, and a reference that is still missing is left out with a note in the plan.

## Preview
- The preview panel is hidden while there is no generation, and the chat takes the full width (content centred at 48rem). It opens with a 300ms width transition when a generation starts or a project with one opens. The user can minimize it; a «نمایش پیش‌نمایش» button at the top of the chat then brings it back and hides again while it is open. On mobile the preview covers the chat until minimized.
- Every generation with a preview has a card in the chat: media on top at full width (a video gets its own player), then «پیش‌نمایش #تولید-۱» and the state. Clicking it opens the panel on that generation.
- While generating, the generation box shows a transparent animated blue gradient, the live status (state, kind and model, real facts only) and a smooth progress bar with an estimated percentage («تخمینی»). The provider reports states, not progress, so the estimate eases towards 95% and reaches 100% only on completion.
- Output media is shown only from a Whoush-owned (same-origin) URL. Provider URLs are never fetched or shown until outputs are mirrored to owned storage (launch gate 8).

## Whoush voice, everyday Persian and Finglish
- Three always-relevant skills (registry 1.2.0):
  - `whoush_voice`: a cool, witty, professional creative friend; 1 to 3 sentences; 0 to 2 emojis; light humor never about the person or anything sensitive; no jokes or emojis around refusals, prices, failures or critical questions.
  - `persian_colloquial`: everyday spoken Persian (محاوره‌ای) with mild friendly slang, «تو», never book Persian or vulgar, political or ethnic slang.
  - `finglish_writing`: active when the brief is Finglish (`lib/finglish.ts`).
- The planner writes `reply.text` (the chat message) in the user's script. A Finglish reply must be Latin letters only (tags excepted); a reply that mixes scripts, leaks internals or fails the plan-text safety check is replaced by Whoush's own line (`VOICE` in `lib/orchestrator.ts`).
- Finglish safety: the lexical prefilter folds Finglish spellings (kh/x, gh/q, oo/u, ee/i, aa/a, digit letters) and checks Finglish forms of every category. It is still only a prefilter.
- Conversation awareness: the last 8 messages go with each message as `history`; each turn is safety-checked, a failing turn is left out, and the planner sees them as untrusted `<history>` data.

## Chat GIFs, emojis and reactions
- Whoush may send a GIF (`reply.gif`, a mood) at a fun moment, never two within its last three turns. The server picks a G-rated GIPHY result for a fixed mood query and keeps only results whose title, creator and slug pass the prefilter and a stricter word list. The images themselves are not inspected; a curated list of approved GIF ids is the production-safe option.
- People send GIFs from the composer's GIF picker (`/api/gifs`, the key stays on the server). A GIF is part of the conversation and of what Whoush remembers, not a brief. The composer's emoji button inserts an emoji at the caret.
- GIPHY media loads from GIPHY's own URLs (no caching or proxying, per GIPHY's developer docs), with «Powered by GIPHY». So the viewer's browser contacts GIPHY directly.
- Off unless `GIPHY_API_KEY` is set; in production also `GIPHY_AUTHORIZED=true`, the owner's assertion that GIPHY's terms and regional availability were checked (the terms page could not be read from here).
- Slack-style reactions: anyone can react to any message from the palette (👍 ❤️ 😂 🔥 😮 🎉 👏 😎 🙌 ✨ 👌 🤩 💯 🙏 🎬 📸); Whoush reacts to the user's message with `reply.react` from the same set. Reactions are saved with the project.
- Anthropic receives a leaner output schema: the full plan schema exceeds its grammar limit, so reply and staging travel as JSON in `extras` (`CreativePlanAnthropicSchema`).

## «ادیت»: brush edit and the edit card (owner, 2026-11-06)
Automatic masking is a later feature. For now:
- **Where:** every uploaded, sent or generated image has a small «ادیت» button (top right, 4px corners). It shows on hover on a computer and is always visible on a phone.
- **Edit card:** when a message asks to change part of a picture without saying where («اینجاشو عوض کن», «با قلم مشخص کنم»), Whoush answers with an edit card that opens it (`lib/edit-card.ts`).
- **Editor (`components/region-editor.tsx`, mobile first):**
  - The picture opens full screen; two fingers pinch and move, or the wheel and the hand tool on a computer.
  - There are five brush sizes, in screen pixels, with a brush-size circle cursor.
  - Every new touch starts a new region with the next colour and tag (#ادیت-۱ … #ادیت-۵). Tapping a region's tag first continues it.
  - Each region has a comment, and its tag pin on the photo has an ✕ to delete it.
- **On «ثبت»:**
  - Whoush makes a marked copy (each region in its colour, translucent), and checks it like any photo.
  - It sends the photo and the copy at once as a new message.
  - The prompt changes only the painted areas, each as its comment says, and locks everything else. The rule leads the plan, and the edit sentence leads the provider prompt.
  - A generated image joins the chat as a new photo (#تصویر-n) to be edited. Marks live in memory only.
